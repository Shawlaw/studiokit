# StudioKit Arcade 生涯首航与剧情流畅度 V2 实施方案

状态：待 main 新发版双端验证完成后实施。方案版本：V2（2026-11-25）。

## 0. 开工条件与分支纪律

1. 等待包含 0.19 触控基线的 main 双端发版完成：远端 main 新提交、对应 GitHub Actions 四项成功、GitHub Pages 与 Cloudflare Pages 逐文件校验通过。
2. 开工时重新 `git fetch origin main`，以最新 `origin/main` 为基线；不以旧本地 main 或 0.18.2 快照为基线。
3. 新建独立集成工作树与分支 `feat/arcade-career-flow`。不污染当前 `feat/arcade-touch-019` 与隔壁 main 工作树，不擅自 stash、commit 或 rebase 其他 Agent 的改动。
4. 若 Owner 仍要求对某已有分支 rebase，只在该分支工作树干净且明确属于本任务时执行；否则从已发布 main 建分支即满足“基于最新 main”的目标。
5. 允许本地提交；禁止 push、PR、merge 到 main、tag、部署。发布仍需单独 `OWNER_AUTHORIZATION: PUBLISH_TO_MAIN`。

## 1. 产品目标

一个完全不了解本项目的玩家，在第一次经典游戏结算后，可以：

- 自行发现并进入旧港，不需要读 README 或由他人解释；
- 明白“我是谁、我在哪、发生了什么、这一单要做什么、做完改变了什么、下一步去哪”；
- 在首两份委托内建立角色身份和第一条完整因果链；
- 沿默认推荐路线持续推进 C0–C5，不会因提示与真实规则不一致而白玩；
- 中断、刷新或次日回来后，能从首页直接知道当前目标并继续；
- 只玩经典游戏的用户不被强制引导、不被弹窗打断。

“沉浸”的验收不是文字量，而是玩家的行动在世界里具有可理解的叙事意义。

## 2. 设计原则

1. **经典侧被动，生涯侧明确。** 经典玩家只看到可忽略的线索；玩家主动读信后，生涯内允许清晰的主按钮与当前目标。
2. **一屏一个主动作。** 其他路线、商店、制造台、材料等作为次要选项或按阶段出现。
3. **先行动，后解释；先人物，后名词。** P-07、E-7、星塔必须在首次出现时就地解释，不提前堆设定。
4. **每份主线委托都有叙事后果。** 即使不解锁新章，也必须产生物件、NPC 回应、路线进展或港口变化，不能连续多局只有工钱。
5. **推荐路线必须服从真实规则。** UI 推荐、章节提示、委托产证和章节旗标由同一事实来源推导，禁止内容层“看起来能过、实际不过”。
6. **不改玩家数据边界。** 不新增/改名 localStorage key，不改生涯 IDB v1/11 stores，不改经典存档与旧机库，不改玩法数值、关卡、计分与经济数值。
7. **不引入构建依赖、远程资源、后端、分析、账号、签到、每日、抽卡或内购。**
8. **兼容 main 的 0.19 触控基线。** 矮视口紧凑模式、拇指区暂停、恢复门和结算防误触不得回退。

## 3. 首航体验（P0，不是后期润色）

### 3.1 第一步：经典结算发现旧物

- 保留被动微线索，不自动弹信、不自动打开生涯。
- 未读线索在同一游戏后续有效结算继续出现，直到玩家读过；不写新线索、不改 Schema。
- chip 移入结算卡片的可视阅读流，位于主按钮附近但不抢占主按钮；文案优先使用有画面感的 `ambientText`，reduced-motion 下静态。
- 首页在有未读线索时，于“继续上次”附近显示一行与既有“旧港来信”同级的小字入口；不放顶层大 CTA、不自动切视图。
- 信件明确玩家身份：刚到折光港、靠接零工维生的自由职业者；说明旧物需要送回旧港。
- 只保留一个主动作“把单据送到旧港”，去掉两个“按地址投递”的语义重叠。

### 3.2 第二步：到港，建立角色与第一个目标

- 使用已写好的 C0 桥段信，但按动作重新编排；不全文倾倒。
- 阿砾作为首航唯一关键 NPC：确认收到旧物、说明免费租机、指定第一份委托，并承诺做完后解释 P-07。
- 告示板首屏只突出一张当前推荐单：游戏名、世界内目标、目标数量、是否需要飞船、推荐原因、主按钮。
- 其余委托折叠为“自由接单”；商店、制造台、材料和复杂经济入口延后展示。
- 第一份委托结算后，港务处把玩家登记为“在册自由职业者”，建立轻量 RPG 身份与成长感。

### 3.3 第三步：首单结算同时交付三种回报

1. 工作回报：工钱与材料（按既有数值）。
2. 剧情所得：航报、现场记录等玩家语言物件，不显示 E/BP/MAP token。
3. 世界反应：NPC 发现异常、旧港广播或灯光变化、下一条具体目标。

收据提供页内“回告示板”和新来信时的“读回信”；不再只有“收起”。回告示板优先在当前游戏页内打开，减少整页跳转。职业结算后“再来一局”不得让玩家误以为仍在做同一委托，文案和出口必须明确。

### 3.4 第四步：第二单形成完整因果链

- 当前目标用玩家语言表达，例如“研究院需要两份来自不同工作的现场记录；你已有航报，再带回一份”。
- 告示板只把当前真正能满足条件的委托标为“推进主线”；其他委托仍可自由接取。
- 第二单后由黎序解释：两份记录为何能相互印证、P-07 是中继密钥、E-7 是十年前失踪的调度员、旧防御系统被港里称为星塔。
- 玩家应形成：捡到旧物 → 送到旧港 → 工作取得航报 → 补齐记录 → 解译 P-07 → 得知 E-7 与星塔。
- 首航结尾给出唯一新目标，例如“去月影遗迹，查清 E-7 当年发生了什么”，随后再逐步放开自由接单和经济系统。

## 4. 默认主线与真实证据路线

默认推荐不是静态硬编码 16 款游戏，而是由当前 quests、claims、证据、已解锁委托和 `route-planner/story-evidence` 共同推导。内容可以提供默认路线偏好，UI 必须验证其当前可执行性。

首选默认路线（用于零种子端到端验收；替代路线仍允许）：

| 顺序 | 真实委托 | 真实产出 | 章节/叙事结果 |
|---|---|---|---|
| 1 | `pendulum-tower.T1` 港口实习 | `C1.work_done` + `E-C1-site` | C1：首份工地记录，建立 P-07 信号线 |
| 2 | `memory-flip.T1` 旧档案夹（中间单） | 无章节证据 | 不跳章，取得档案整理经验与路线进展 |
| 3 | `memory-flip.T2` 差一张的照片 | `E-memory-flip.T2` | C2：两份不同工作记录凑齐，解译 P-07 |
| 4 | `shadow-leap.T1`（中间单） | 无章节证据 | 不跳章，取得月影坐标与路线进展 |
| 5 | `shadow-leap.T2` 失落卷轴 | 第三份 E | C3：月影时间差拼合，理解 E-7 与旧防御 |
| 6 | `pendulum-tower.T2` 码头脚手架（中间单） | `E-C1-site-2` | 不跳章，补充工地记录并推进供电准备 |
| 7 | `gomoku.T1` 布局练习（中间单） | 无章节证据 | 不跳章，取得疏散布局与路线进展 |
| 8 | `gomoku.T2` 破解防线 | `E-gomoku.T2` | C4：五份跨游戏现场记录齐备，城市供电恢复 |
| 9 | 玩家选择三终局之一 | C5 + ending.* | 后日谈与港口状态变化 |

该路线避免 C2/C3 在同一结算瞬间连跳，同时保证中间单也有明确叙事反馈。内容作者可按叙事一致性微调默认路线，但不得破坏以下不变量：

- 每个“完成本章”的推荐路径按真实规则计算后确实会授予对应旗标；
- 中间单必须标明“路线进展”而不是伪装成“完成本章”；
- 若一次结算真实满足多个章节规则，UI 以当前章和最新完成章为中心呈现，不全量展开所有章节；
- 任何替代推荐同样经过真实规则验证。

## 5. C2–C5 内容重写（与首航同批 P0）

每章至少三类节拍，可在 `chapter-XX.json` 中以向后兼容的可选内容字段表达：

1. `start`：谁提出目标、为什么；
2. `progress`：中间单或部分证据后的反馈；
3. `complete`：新事实、世界变化和下一步。

要求：

- 每章正文不再只有一句结论；结论可以放入“已知事实”，场景与人物回应作为正文。
- E-7、星塔在需要之前完成铺垫；三终局在 C4 前有各自价值立场与行为预告。
- NPC 回信与收据/章节动作绑定，不再只等玩家偶然打开章节面板。
- `handoff` 真正渲染为下一目标；章节面板以“当前章 + 最近完成章”为主，其余折叠。
- 玩家可见文案不出现 C0/C1、active/locked、E/BP/MAP、长凭据号等内部记号；测试选择器可继续放在 data 属性。
- 工钱/信用点、旧港/折光港、旧港来信/章节等对外术语统一；经典星币与生涯信用点明确区分。

## 6. 导航、反馈与连续性

1. **枢纽解耦**：优先实现低风险枢纽模式——面板打开时隐藏宿主游戏画布与开局 UI，关闭面板回到街机厅对应视图，不让玩家落在层塔开局界面。若该方案仍造成明显上下文问题，再做独立轻量面板宿主页。
2. **委托循环页内化**：结算 → 收据 → 当前页告示板 → 接单时才整页跳转；目标为每单至多一次必要整页跳转。
3. **即时反馈**：结算路径使用 `recordFromReceipt` 的真实返回值，新增章节/路线进展必须透传给收据；失败如实显示，不能收据成功但证据静默丢失。结算时补做幂等 C1 同步，不再依赖下次打开面板。
4. **告示板信息**：卡片显示游戏名、世界内目标、目标数量、推荐原因、是否推进主线；删除 96 条完全相同的伪时长信息；产证差异用玩家语言表达。
5. **渐进披露**：首航只展示当前所需入口；商店/制造台/材料/职业等级等在玩家需要时出现，不全屏一次性摊开。
6. **首页动态状态**：生涯卡显示当前目标、未完成委托、未读信、最新章节进展；经典续玩与生涯委托明确区分。
7. **继续委托**：关标签导致 sessionStorage ticket 丢失时，依据既有 live run 显示“继续这张单”；玩家显式点击后恢复会话 ticket 并进入正确游戏，不自动接管当前页面。
8. **刷新说明**：本局事件缓冲仍按既有架构处理；恢复时明确告知未结算临时进度需重打，不静默判失败。
9. **失败与扣费**：失败显示真实差距和一键重接入口；代办“钱已扣、旗标未记”等结果不得被通用文案吞掉，文案改为戏内语言。
10. **返回语义**：生涯相关返回落到来源视图/面板；浏览器后退/Android 返回键与 Esc 一致，必要时接入 history 栈，不直接意外退页。

## 7. 技术边界与接口

- 内容 JSON 可做向后兼容的可选字段扩展；不改变既有 IDB 行结构和 localStorage Schema。
- 优先复用 `chapter-01.json` 已有 beats、`route-planner` 的 missing/blocker 能力和 `story-evidence` 的真实规则，不另建一套平行规则。
- 若 `campaign-core`、`story-evidence`、UI 之间需要新接口，先在 ADR 增补冻结：输入、输出、失败语义、旧内容回退、测试选择器。
- 剧情展示状态尽量从既有 quests/claims/discovery 推导；折叠、滚动位置等会话 UI 状态不写存储。
- 首页只读既有 IDB stores，不为首页提示创建生涯档案。
- 所有 UI 支持 320/375/390/430、0.19 的 375×548/390×664 等紧凑视口、键盘、读屏、reduced-motion、44px 热区。
- GitHub Pages 子路径、Cloudflare 根路径、带 `.html` 与无后缀 URL、离线 PWA 均保持兼容。

## 8. Subagent 工作流与文件所有权

开工后由主 Agent 建集成工作树，各 Agent 使用独立工作树/分支，禁止相互覆盖。

### A. 内容与叙事

- 负责 `apps/arcade/career/content/*.json`。
- 首航身份、NPC 台词、C0–C5 节拍、默认路线、真实路线提示、术语统一。
- 与 B 先冻结内容字段和路线不变量，再写内容。

### B. 生涯核心与规则接线

- 负责 `career/bridge.js`、`campaign-core.js`、`story-evidence.js`、`route-planner.js`、`commission-core.js` 及必要的核心纯函数测试。
- 结算时旗标同步、证据结果透传、真实推荐/缺口推导、live run 恢复、错误语义。
- 不改 IDB Schema；所有失败保持幂等、fail-open、不伪造成功。

### C. 生涯面板与交互

- 负责 `career/ui/*.js`、`career/ui/clue-surface.css`。
- chip、信箱、告示板、收据、章节面板、渐进披露、面板内导航、可访问性。
- 不改 `apps/arcade/index.html` 与 `arcade.css`，避免与 D 冲突。

### D. 首页、枢纽与共享样式

- 负责 `apps/arcade/index.html`、`apps/arcade/arcade.css`、必要的站点内返回逻辑。
- 首页动态状态、未读线索入口、枢纽模式、视图返回、紧凑布局。
- 不改 career 核心与 UI 文件。

### E. 测试与证据

- 负责新增/更新 `tools/` 测试，不改产品实现。
- 先写会失败的验收测试，再随集成迭代；与主 Agent 预约独占 Chrome 时段。
- 其他 Agent 默认只跑 `node --check` 和纯 Node 测试；所有 Chrome/聚合门禁由主 Agent 或 E 串行执行。

### 集成纪律

1. 每批先对齐接口，再并行实现；各 Agent 只 add/commit 自己拥有的文件。
2. Conventional Commits，一个提交一个意图；禁止 squash/rebase/force-push 他人分支。
3. 主 Agent 按 A/B/C/D 批次集成，先跑静态与窄范围测试，再交给 E 跑浏览器验收。
4. 失败回灌责任工作流，修复后重跑；不伪造门禁结果。
5. 每批更新设计文档与未解决项，不用“基本完成”代替可验证结论。

## 9. 迭代批次

### 批次 1：首航可读可玩

- 未读线索可找回、首页小字回流、信件单一主动作。
- 首两张推荐单、角色身份、首航桥段信、收据三回报与下一步。
- 结算时 C1/证据反馈接线。
- 枢纽模式与基础生涯返回。
- 验收：新档到第二单后形成完整因果链；每单至多一次必要整页跳转；不错过 chip 后永久失联。

### 批次 2：默认主线与真实规则

- 默认路线到 C4、每章 start/progress/complete 节拍、真实缺口和推荐。
- 路线一致性测试、默认路线零直接写旗标 E2E、内部 token 清理。
- 验收：按界面默认推荐可推进；没有“按提示做却不产证”；中间单有反馈；不会一次倾倒六章。

### 批次 3：连续性与全平台

- 继续未完成委托、刷新说明、失败重接、动态首页、历史返回。
- 320/375/390/430 与 0.19 紧凑视口、键盘/读屏/reduced-motion、PWA 离线与两种部署路径。
- 经典模式、挑战、禅、割草、旧机库、localStorage/IDB 数据零回归。

### 批次 4：收口与独立复审

- 全量聚合门禁串行运行，必要时独立单项重跑并记录环境偶发。
- 独立 Reviewer 从产品逻辑、叙事一致性、数据兼容和测试真实性复审。
- 输出 Owner 试玩包、默认路线清单、已知边界、回滚说明。
- 不发布，等待 Owner 试玩与明确发布授权。

## 10. 测试与验收

### 自动化

1. **路线一致性不变量**：每个展示给玩家的主线推荐，按其要求模拟完成后，真实规则必定产生对应章节旗标；中间步骤必须明确标注不完成章节。
2. **零剧情种子 E2E**：全新档案，不直接 `putQuests`、不写章节旗标、不预置 tier 进度。允许用游戏自带测试钩子完成真实玩法事件，但入口、读信、接单、导航、结算和章节阅读必须走真实 UI。
3. 未读线索错过后可找回；首两单因果链；每单下一步；章节完成当前屏反馈；刷新/关标签后的继续；失败重接与扣费提示。
4. 玩家可见文本扫描：无内部章节状态、证据 token、长 runId 等调试信息。
5. 既有 career/arcade 全量回归与经典 localStorage 金样；PWA 离线、GH 子路径、CF 无后缀。
6. 320/375/390/430 与 0.19 紧凑视口布局、44px、焦点、Esc/返回、reduced-motion。

### 真人首航验收（不能由自动化替代）

找未接触过项目的玩家，不做口头讲解，观察首两份委托：

- 能复述自己的身份、P-07 是什么、E-7 是谁、星塔是什么、下一步为什么；
- 无需提示能开始第三份委托；
- 不把信用点与星币、生涯机库与经典机库混为一谈；
- 次日回来后能根据首页说出当前目标并继续；
- 没有明显“我以为这单会推进剧情，结果什么都没有”的时刻。

这些是需要实测的目标，不在未试玩时宣称已通过。

## 11. 文档与回滚
